## 1. 语义与参考的边界

### 四项具体自审，不能泛泛而谈

| 问题 | 必须给出的可核对答案 |
| --- | --- |
| 不同东西用什么符号？ | 列出本图对象类型与实际符号的对应，以及哪些文字有框、哪些无框 |
| 不同层次如何联系？ | 逐条说明关键箭头的源、目标、内容、方向，核对总线和反馈回路 |
| 各层权重如何表达？ | 说明实际的归属、位置、尺寸与颜色如何对应职责；不能把任意大小解释成重要性 |
| 每个图标有什么意义？ | 解释它标识的对象类型或真实信息；解释不出信息增量就删除 |

用户要求解释时，以上答案要针对正在修改的具体图给出；不要只回答“美观、清楚、有层次”。

架构图同时回答三个问题：有什么对象、对象如何协作、哪些对象属于同一类。只给每个模块一个框并不能回答后两个问题。

整理新图时，先形成一个简短的对象清单和关系清单，不必把清单当成额外交付物：

| 要核对的事实 | 对画图的影响 |
| --- | --- |
| 对象是 Agent、操作、产物、输入还是基础设施 | 决定符号，而不是看哪个图标好看 |
| 对象由谁控制、给谁提供支持 | 决定归属、箭头目标与图上位置 |
| 多个动作是并行执行、顺序执行、择一选择还是仅表示可用能力 | 决定分发、串行、条件或无顺序的能力清单 |
| 箭头传任务、结果、状态还是反馈 | 决定方向、标注和颜色 |
| 算法名、项目名、阶段名分别是什么 | 避免把 Post-route 与 A2-ORFO 当同类标签 |

正文与图注决定业务内容，参考论文决定可以借鉴的组织手法。可以借鉴“白框圈定 Agent、蓝框表达内部流程”，不能把参考论文中的 Teacher/Student 等角色自动放进另一篇论文。

论文没有提供某组件的独立项目名，就去掉多余标签或直接使用已知组件名。不要为了外观对齐发明一个项目名称。

## 2. 最终视觉语法与例外

“文字都应有归属”不等于“每段文字都必须套框”。最终接受的语法如下。

| 对象 | 默认外观 | 文字如何摆放 | 不采用的做法 |
| --- | --- | --- | --- |
| 系统层级 | 连续浅色背景板，上方较深层名条 | 层名直接放条内 | 每层随意切成孤立卡片 |
| Agent 范围 | 白色外框，统一蓝边 | 顶部红色名字及小机器人 | Agent 与普通内容框完全同形同色而无身份标记 |
| Agent 内部步骤 | 浅蓝底、蓝边、相同级别统一尺寸 | 步骤动作/依据放框内 | 在名字下面裸列无归属短句 |
| Context and Prompt | 有边界的输入面板 | 类别可用深蓝白字，内部内容明确 | User objective / Design context 的装饰图标 |
| 具体输入实例 | 独立示例面板 | 设计/工艺/约束及示例请求分框 | 用实例冒充原论文逐字给出的实验 prompt |
| 数据与执行底座 | 同风格圆柱 | 蓝色标题无框，能力清单白框 | 橙色标题、重复小图标、裸列能力词 |
| 关系标签 | 无框纯文字 | 放在线旁，留清楚间隙 | 给 Query、Evidence 等每个词加框 |
| 算法/项目注释 | 仅在需要时出现 | 与名称、步骤、阶段保持语义一致 | 为补空白放方法名胶囊框 |

本用户明确采用圆柱同时表示数据底座和执行底座：这里表达的是共享基础设施，不是在声称执行服务是一种数据库。面向其他读者或更换符号规范时应重新核对，不能机械地要求任何服务都用数据库符号。

小机器人是 Agent 类型标记，不表示系统实际部署了机器人，也不表示模型规格。新图从 Flaticon 选取对应图标，并按 [图标来源与 PPT 可编辑交付](icons-and-editability.md) 转成原生可编辑对象。基础设施小图标的删除是该历史样例的选择，新图按语义安排适量图标。

## 3. 层级、归属和视觉权重

支持型诊断 Agent 与实际修改设计的优化 Agent 可以同属专业层，但不一定是同一种执行角色。最终样例把 Analysis Agent 放在优化动作子范围之外，用位置与归属完成区分。不要把它画得更大、更艳、更多图标，制造虚假的主角。

Control Agent 需要展示决策链，因此适合竖列。专业动作各自是一个小系统，因此适合白色范围框中的横向流程。共享底座需要表达被多个角色复用，因此使用统一基础设施区域。层级是职责划分，不是从上往下堆四行标签。

面积应根据内容长度、步骤数量和路由通道分配。Agent 标题、步骤字号、边框、箭头采用统一规则。不要把“模型觉得重要”当成增大模块的理由，也不要声称不同箭头长度代表权重——长度通常只是路由距离。

论文空间优先给流程和关系：

- 删除没有信息增量的图标和重复方法标签。
- 不为了“看起来完整”恢复已经删除的底部图例和反馈说明句。
- 短路径标签就近标注，不加边框占据通道。
- 保持基础设施能力在白框内，避免圆柱里文字随意漂浮。
- 外部输入的示例应服务于读者理解；不要压过真正的系统主体。

## 4. 连接关系与箭头拓扑

优先级是语义正确、连接无歧义、不穿字或无关对象、路线简洁，再考虑对齐和对称。不能为了视觉均匀而改变关系、增加虚假顺序。

### 4.1 先区分发起、回传、状态复用和记录

先确认每条线的语义，再决定走线。例如：Control 下发诊断任务，Analysis 返回发现；专业工作流请求数据并得到证据；执行底座复用状态、向数据底座记录结果。这里的例子只说明审视方式，具体关系以当前论文为准。

两个方向都存在时，用错开的单向线分别标清。不要因为两个模块互相通信，就直接画一条蓝色双箭头。双箭头会隐藏“谁请求什么、谁返回什么”。

双箭头并非任何场景都错误：只有当它确实表示不可分解的对称关系、且不会混淆载荷与时序时才使用。请求与证据、动作与测量是不同关系，应分别表达。

线应接到真正对象：Agent 任务接 Agent 范围边界，明确的步骤输入接步骤。跨模块总体通信可接范围框，不必假造其内部每一步都直接访问底座。

对关键线记录源、目标、载荷、方向和触发条件。顺序、作用范围、条件触发、状态装载和持久化不是一种关系：使用位置、线型和短标签区分，不能全部压成无说明的实线箭头。虚线表示适用范围时，通常不需要伪造数据流箭头；表示周期执行时则标明 Periodic / 条件。

同类关系保持线宽和箭头头部一致。长度由节点和通道决定，不擅自解释成权重；粗细、渐变或色差若表达数值，必须有真实依据与可读说明。

### 4.2 分发总线

总线入口与分支出口不是两次任务传递。入口到主干用普通线，主干用普通线，只有进入目标的分支带箭头。不要在进入子范围时画一个箭头头部，几何上再接一条没有连续性的横线。

源到三目标时，主干是一条连续竖线，三条分支精确落在主干上。线端不能只“接近”主干：PPT 重渲染时细小断点会变成明显裂缝。

分发与汇合不同：分发箭头在目标入口，汇合后箭头指向真实接收方。交叉也不等于连接；优先改通道避免歧义，不用装饰圆点补救不准确几何。不要把能力清单的多项操作连成无依据的顺序。

主干放在通道中央，避免直到目标边界附近才分叉。分叉过晚造成右侧箭杆极短、箭头头部拥挤，与左边很长的输入线失衡。

### 4.3 回路

如果 Review 回到前面的步骤，优先画：从 Review 左边出来，沿左侧通道上行，再向右进入前面步骤的左边。只有端口、实际障碍或语义要求不允许时，才用更多折点。

不要用“上行—右行—再上行”解决一个本可直接右转进入的端口；多一个折点不增加信息。

左侧通道必须同时容纳外框间隙、竖线、右转箭杆和箭头头部。若只有一个三角形而看不到水平箭杆，不能说箭头已经正确：要左移回路或调整范围边界。不要把箭头缩成另一套尺寸来掩盖通道不足。

外部输入箭头和内部回路线进入同一步骤时，使用不同纵向锚点，避免压在同一点上或让箭头头部互相覆盖。

### 4.4 底部外回路

回路跨越整个平台时，水平线贴近背景板下沿但不接触。检查的距离是线到背景板的真实间隙，不是线到页面底边。

下移外回路会同时扩大整幅图的高度和无效空白。删除底部图例/说明后应收紧画布。不同图的间隙可不同，最终样例的 15 单位只是一条经过确认的参考值。

## 5. 等距、对称、通道和回路的计算

### 5.1 等距步骤列，同时满足跨列对齐

设步骤框高为 h，第一个框中心为 c0，第 k 个框（从 0 开始）必须对齐右侧中心 a：

```text
d = (a - c0) / k
center[i] = c0 + i*d
top[i] = center[i] - h/2
gap = d - h
```

必须有 d > h。相邻箭头几何长度按相同端点留量扣除，不能有的扣 1、有的扣 10。

最终确认的五框样例：

```text
h = 110
c0 = 335
k = 3
a = 925
center = [335, 531.6667, 728.3333, 925, 1121.6667]
top = [280, 476.6667, 673.3333, 870, 1066.6667]
box gap = 86.6667
arrow length = 84.6667  # 每端各留 1 单位
```

因此第四个步骤中心与右侧中间分支同为 925，所有竖向箭头等长。不能保留前面三个位置不动，只移动第三个框，然后仍把最后一根长箭头留在那里。

### 5.2 分叉通道中点与上下对称

设源步骤右边为 xs，目标 Agent 左边为 xt，通道不受其他障碍影响时：

```text
bus_x = (xs + xt) / 2
middle_y = (top_branch_y + bottom_branch_y) / 2
source_y = middle_y
```

样例中 xs=1120、xt=1340，主干 x=1230。分支 y 为 665、925、1185，相对于中间各为 260。导出为避免边框重叠采用 1121/1339 的线端，其两段仍各为 109。

这不是要求所有多分支必须绝对对称。条件不对称、目标数量不同或存在障碍时可不对称，但要说明真实结构，不能随意画乱后用“逻辑复杂”解释。

### 5.3 回路的简单几何

源和目标都从框左边进出，通道位于两者左侧：

```text
(source_x, source_y)
(rail_x, source_y)
(rail_x, target_y)
(target_x, target_y)
```

最终样例 rail_x=680，target_x=729，进入目标前的水平段长 49；原先长度 29 显得拥挤。Agent 左边界同时从 690 扩到 670，给回路留出空间。

箭头头部尺寸是实际渲染值，不能只看坐标差。最后一段应有清晰可见的箭杆；常可先留约 1.5–2 倍头部长，再按实际导出图检查。有限空间无法满足时应调整通道/范围，不采用穿框或缩小局部箭头的办法。

### 5.4 最小可运行检查

```python
assert max(gaps) - min(gaps) < 1e-8
assert abs(source_y - middle_branch_y) < 1e-8
assert abs((middle_y-top_y) - (bottom_y-middle_y)) < 1e-8
assert all(x1 == x2 or y1 == y2 for (x1,y1),(x2,y2) in segments)
```

使用 [layout_math.py](../scripts/layout_math.py) 可直接计算这些约束。只检查当前图需要的几何，不引入完整布局引擎。

## 6. 高发失败与具体修正

| 失败 | 为什么不成立 | 修改 |
| --- | --- | --- |
| 先选很多图标再塞内容 | 图标不解释对象，只占空间 | 先定义类型，仅保留有类型含义的标记 |
| 机械执行“所有文字加框” | 路径标签和标题的归属已经清楚 | 内容框保留，路径/标题去框 |
| 四个 Agent 并列同级 | 支持诊断与执行优化的关系被抹平 | 用子范围与位置区分，不放大支持角色 |
| Agent 只有标题与图标 | 看不出它作为系统如何工作 | 依据论文画内部操作链 |
| 同时写 Review / Revise 且不解释 | 用户会追问为什么两个词、是否两次动作 | 用明确的 Review QoR & next action 等内容 |
| 项目标签混进 Post-route | 项目名与阶段名不是同类 | 去掉不必要标签，不编造替代项目 |
| 粗细、颜色、大小不统一 | 没有语义，像随机装饰 | 建立少量类型规则，统一线宽和字号 |
| 末根流程箭头特别长 | 手工坐标积累，局部改动未联动 | 用锚点约束反算整列等距 |
| 总线靠右、目标入口很挤 | 分叉位置太迟 | 主干移到可用通道中点 |
| 源线与中间分支错开 | 看着像额外转接，上下失衡 | 对齐源步骤中心和中间分支 |
| 回路向右再向上 | 端口与空间未经审视 | 左侧上行后直接向右入框 |
| 右转箭头只剩三角形 | 最后线段太短 | 左移主干并给范围边界留空 |
| 底部红线远离背景 | 浪费图高、视觉重心向下拖 | 靠近背景边缘，保留间隙并裁掉空白 |
| 输出 PPT 只是整图 | 用户不能修改字、线和流程 | 原生对象制作并检查无整幅栅格替代 |
| 导出后没回看 | 可能丢箭头、错换行或出现断线 | 重新导入最终文件并逐区检查 |

## 7. 新图与局部改图的操作方式

新图依次解决：内容来源、对象类型、归属层级、连接语义、主布局、几何约束、文字与颜色、导出。

局部改图按用户编号逐项改，保留已确认的部分；不要每轮顺手重新排版、加图标或恢复旧内容。用户说“这个终于可以了”后，该版是比较基线；下一轮以局部差异为主。

收到新指令时，把它并入当前修改，不丢掉此前尚未完成的要求。对“第三个框下移”这类自然语言理解其目标：用户在要求箭头均匀与跨列对称，不能只移动一个框就交差。

如果用户追问不同符号、箭头、权重和图标的意义，逐项指向当前图里的具体对象作答。颜色代表什么、大小为什么不同、箭头是否真指向目标，都要能由图与论文验证，不能只回答“层次清晰、逻辑直观”。

后续多轮形成的压缩、字号、机制解释与系列区分规则见 [构图、文字与系列风格](composition-and-typography.md)，实际状态和适用边界见 [后续案例](case-studies.md)。最终审查按 [审查与验收](quality-review.md) 执行。
